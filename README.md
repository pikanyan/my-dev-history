# My Dev History

※ 長い期間を振り返って書いているため、時期や順番はおおよそのものです。

## 2015 年 (20 歳): プログラミングへの興味

-   きっかけ:
    友人の「キャラクターがマウスカーソルを追いかけるアプリ」を見て、
    仕組みを作る側に興味を持つ。

-   初めての言語:
    学習コストよりも、「仕組みを理解すること」を優先し、C 言語 を選択

-   当時の学習スタイル:
    小さなサンプルを大量に書いては試す練習が中心で、
    成果物の多くは残っていないが、
    基本文法と、「書いて確かめる癖」がこの時期に身についた。

-   購入書籍:
    苦しんで覚える C 言語

## 2017 年 (22 歳): Windows API による GUI 制作

-   背景:
    就職を意識し始め、「中卒というハンデを埋めるには差別化が必要」と当時は考えていた。

-   最初の制作:
    手順が明確な教材を用いて、Sunaba という言語でテトリスを作成し、完成体験を得る。

-   次の制作:
    仕組みをより深く理解したくなり、C 言語 + Windows API でテトリスを作成

-   この時期に身についたこと:

    -   イベント駆動の流れ
    -   ウィンドウシステムの基本構造への理解

-   反省点:

    -   「完成」より「理解」を優先しがちで、成果物を育てる習慣が弱かった
        この癖が、後年の「学習量の割に成果物が薄い」という課題に繋がった

-   購入書籍:
    -   猫でもわかる Windows プログラミング
    -   API で学ぶ Windows 徹底理解

## 2020 年 (25 歳): 設計、デザインパターン

-   背景:
    機能が増えるにつれコード量が膨らみ、読みづらさと保守性の限界を感じた。
    「このままでは仕事として通用しない」と思い、整理の手法を探し始めた。

-   取り組み:

    -   デザインパターン を集中的に学習。
    -   書籍理解のために言語 Java も学習し、学んだ内容を言語 C++ に置き換えて試した。
    -   当時は中卒コンプレックスもあり、「深く理解できそうな難しい方向」へ寄りやすかった。

-   つまづき:

    -   パターンを読めても、「この状況で使う理由」と「得られる効果」が腑に落ちず、実践に応用できなかった。
    -   結果として、制作よりも、パターンごとの整理や比較検討大半の時間を使う "沼" に入り、成果物として残りにくい時期が続く。

-   学び:

    -   手法の暗記だけでは設計はできない。
    -   目的 (変更に強い / 読み易い / テストし易い) や仕様から逆算しなければ、最適なパターンを選択できない。
    -   当時は SOLID の原則などの判断軸を知らず、選び方を体系化できていなかった。
    -   しかし、考え続けること自体はずっと楽しかった。

-   当時の試行錯誤:

    -   カオスを抑える道具のために、リーダブルコード / UML / 関数型にも触れた。
    -   Windows API の最小アプリをクラス化する練習もしたが、
        インターフェースとカプセル化の判断軸が持てず、迷った。
    -   この経験が、後の WinForms や WPF、Qt への学習動機に繋がる。

-   購入書籍:
    -   Java 言語で学ぶデザインパターン入門
    -   ロベールの C++ 入門講座
    -   すごい Haskell たのしく学ぼう
    -   オブジェクト指向でなぜつくるのか

## 2022 年 (27 歳) 前半: フレームワークで「正解の手触り」を得る

-   背景:
    アプリ自体は制作できても、規模が大きくなるとカオス化する問題が続いた。

-   新たな発見 (1 つの正解):

    -   WinForms に触れることで、Windows API の負担をフレームワークが吸収してくれると実感。
    -   自作で試行錯誤するより、まずは「枠組みに乗る」方が近道だと気づく。
    -   WinForms も一長一短はあるが、完成まで持っていく為の現実的な手段だと感じた。

-   視野の拡張 (構造の視点):

    -   WinForms よりモダンなものを求め、WPF に触れることで、MVVM を知る。
    -   更に、MVC にも触れ、「画面」だけでなく「アプリ全体」の設計を意識し始める。

-   視野の拡張 (依存先)

    -   SQL や DB 設計にも取り組むことで
        依存先は「テーブルなどの変化が少ないもの」を中心に考える発想に出会った。
        後に、クリーンアーキテクチャの理解にも繋がる。

## 2022 年 (27 歳) 後半～現在: 実用性と学習継続へ方針転換

-   背景:
    業績悪化をきっかけに、開発職への転職を現実の目標として定めた。

-   方針転換:
    -   「差別化」より「現場で再現性が高いスキル」を優先するように切り替えた。
    -   具体的には、TDD や git / GitHub を取り入れ、作業を手順化する。

-   環境の選択:
    -   Python / Django を選び、枠組みに乗って "動くものを早く作る" ことを重視。
    -   選択肢が多すぎる環境で停滞しやすい自分に対して、前進しやすい道を選んだ。

-   進め方:
    -   まずは、資格で基礎を体系化し、用語と前提知識を準備。
    -   その上で、小さくても業務に近い要素 (CRUD / 画面 / データ設計 / テスト) を入れた成果物を制作。

-   今に活きている点:
    -   触れた範囲が広いからこそ、「何をやらないか」を決め、優先順位をつけて継続できるようになった。
