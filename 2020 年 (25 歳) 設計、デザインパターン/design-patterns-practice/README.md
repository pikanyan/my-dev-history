# design-patterns-practice

## 1. これは何か

-   複数書籍で学んだ デザインパターン / 設計 の練習コード集です。
-   写経だけで終わらせず、**適用前 / 適用後の比較**や**自分なりの書き換え**で理解を深めた履歴を残しています。
-   目的は「パターン名を知っている」ではなく、**業務で使える判断軸**を作ることです。

## 2. 見て欲しいポイント (迷ったらここ)

-   デザインパターンの学習記録を最短で伝える為に、`抜粋` フォルダを用意しました。
-   Strategy パターンの適用前、適用後を 1 セットで見れるようにしています。
-   各フォルダの `00 class.png` は `00 class.puml` というテキストベースの UML 定義ファイル を画像化しただけのものです。

### 2.1 抜粋フォルダ (Strategy パターンの比較)

-   `抜粋/01 Strategy でない + implements を使わない継承/`
    -   意図: extends だけだと、「実装したくないこと」まで抱える不自然さが生まれる

-   `抜粋/02 Strategy でない + implements を使う継承/`
    -   意図: implements で自然になるが、振る舞いの組み合わせが増えると、結合度が大幅に上がり、破綻しやすい

-   `抜粋/03 Strategy である/`
    -   意図: 振る舞いを差し替え可能にして、疎結合にする (SOLID の原則の DIP)

### 2.2 補足 (読みたい人だけ)
-   01 の補足:
    -   DecoyDuck (偽物のダック) は飛べず、鳴けないので、Duck の実装を上書きする必要がある
    -   RubberDuck (ゴム製のダック) は飛べず、ゴムの鳴き声がするので、同様に上書きする必要がある

    -   extends 単体では "実装したくないこと" を "実装する" 不自然さがある
    -   継承なので、インターフェースの形に依存し、密結合になる

-   02 の補足:
    -   MallardDuck (マガモ) は飛べる上に、鳴けるので、Flyable や Quackable を implements する
    -   DecoyDuck (偽物のダック) は飛べず、鳴けないので、何も implements しない

    -   implements を用いることで、"実装したいこと" を "実装する" ので自然にはなる
    -   しかし、実装可能な対象のバリエーションが少ない
    -   これも同様に継承なので、インターフェースの形に依存し、密結合になる

-   03 の補足:
    -   QuackBehavior を実装する鳴き声が Quack だけでなく、Squeak もあり、バリエーションが多くなる
    -   Duck 抽象クラスは、FlyBehavior interface や QuackBehavior interface という変化が少ない interface を保持するだけなので、疎結合
    -   SOLID の原則の DIP の典型例
